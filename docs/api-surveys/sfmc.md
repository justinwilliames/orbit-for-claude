# Salesforce Marketing Cloud Engagement — capability survey

**Platform key:** `sfmc`
**REST base URL:** `https://<subdomain>.rest.marketingcloudapis.com` (the `rest_instance_url` returned by the token call)
**Auth base URL:** `https://<subdomain>.auth.marketingcloudapis.com`
**SOAP base URL:** `https://<subdomain>.soap.marketingcloudapis.com/Service.asmx`
**Auth:** OAuth2 `client_credentials` against `POST /v2/token`. **Access-token lifetime is 20 minutes**, but the response's `expires_in` is deliberately `1080` (18 minutes) because Salesforce recommends refreshing two minutes early. The docs are explicit: *"Don't request a new access token for every API call you make — each access token is reusable, and remains valid for 20 minutes… causes throttling"* (<https://developer.salesforce.com/docs/marketing/marketing-cloud/guide/access-token-s2s.html>).
**Templating:** AMPscript (plus Guide Template Language / `%%[ ]%%` blocks in Content Builder).

**API version:** SFMC has **no single global version**. Each REST family carries its own path version segment (`/asset/v1`, `/interaction/v1`, `/contacts/v1`, `/data/v1`, `/automation/v1`, `/messaging/v1`, `/platform/v1`, `/hub/v1`) and the OpenAPI documents Salesforce publishes for those families are versioned `"1"`. The SOAP API is a single WSDL (`Service.asmx`) with no version segment.

**Verified against live docs:** 2026-08-24. Endpoint inventories below were read from the OpenAPI (OAS 3.0.2) documents that back the published reference pages at `developer.salesforce.com/docs/marketing/marketing-cloud/references/*` — e.g. `mc_rest_assets/assets.yml`, `mc_rest_automation_studio_automations/automations.yml`, `mc-custom_objects/customObjects.yml`, `mc_rest_transactional_messaging_email/transactional_messaging_email.yml` — plus the markdown reference pages for the families Salesforce does not publish as OAS (Journeys, Contacts, Messaging, Event Notification, Seed List).

**Rate limiting.** Salesforce publishes no hard numeric REST quota. It documents variable throttling: REST throttling returns **HTTP 429** and SOAP throttling returns **HTTP 500 with a `Rate Limited` fault** (<https://developer.salesforce.com/docs/marketing/marketing-cloud/guide/rate-limiting.html>, <https://developer.salesforce.com/docs/marketing/marketing-cloud/guide/rate-limiting-errors.html>, <https://developer.salesforce.com/docs/marketing/marketing-cloud/guide/rate-limiting-best-practices.html>). Any adapter must treat throttling as a normal outcome, not an outage.

**The REST/SOAP split, stated once.** SFMC's REST API covers Content Builder, Journey Builder, Contact Builder, Data Extensions, Automation Studio, transactional messaging, domain verification, seed lists and event notifications. It does **not** cover Email Studio's classic primitives: subscriber **Lists**, **ListSubscriber** membership, **Send** (send-job aggregate tracking), the individual **tracking events** (SentEvent/OpenEvent/ClickEvent/BounceEvent/UnsubEvent), **suppression lists**, and the **sender/delivery/send-classification** profiles. Those are SOAP-only, all confirmed against the supported-operations matrix at <https://developer.salesforce.com/docs/marketing/marketing-cloud/guide/supported_operations_for_objects_and_methods.html>. Every SOAP-only row below is flagged as such.

**Scopes.** SFMC gates every REST route on an Installed-Package scope. The authoritative route→scope table is <https://developer.salesforce.com/docs/marketing/marketing-cloud/references/mc_rest_rest_permission_scopes/rest-permissions-and-scopes.html>; the specific scope is named per row below wherever Salesforce documents it. An SFMC integration that only requests `email_read` will fail on assets, journeys and contacts — Orbit's `checkAuth` should say *which* scopes it proved.

### Write-side operations that exist but should be flagged **do-not-automate**

Recorded here so Orbit never implies these are safe to fire unattended, per the read-first bias:

- `POST /interaction/v1/events` — fires a journey entry event for a live contact (<https://developer.salesforce.com/docs/marketing/marketing-cloud/references/mc_rest_interaction/postEvent.html>).
- `POST /interaction/v1/interactions/publishAsync/{id}` / `postStopInteractionById` / pause / resume — mutate a **live** journey (<https://developer.salesforce.com/docs/marketing/marketing-cloud/references/mc_rest_interaction/postPublishInteractionById.html>).
- `POST /messaging/v1/email/messages` (multiple recipients) — a real bulk send, not a proof.
- `DELETE /messaging/v1/email/definitions/{key}/queue` — discards queued messages.
- `POST /contacts/v1/contacts/actions/delete?type=…` and `.../restrict?type=…` — irreversible contact deletion / restriction (<https://developer.salesforce.com/docs/marketing/marketing-cloud/references/mc_rest_contacts/DeleteByContactKeys.html>).
- `POST /data/v1/customobjects/{id}/cleardata` — wipes a data extension.
- `POST /automation/v1/automations/{id}/actions/runallonce`, `/automation/v1/automations/trigger` — executes an automation.
- `POST /data/v1/bulk/ingest` family and `PUT /hub/v1/dataevents/...` — bulk data mutation.
- `DELETE /asset/v1/content/assets/{id}` — destroys stored content (`PATCH .../archive` is the reversible alternative).

## 4. Implementation notes for the SFMC adapter

1. **Two hosts, not one.** Auth is `https://<subdomain>.auth.marketingcloudapis.com/v2/token`; everything else uses the `rest_instance_url` from the token response. Never hard-code the REST host from the subdomain — Salesforce's own docs say to use the returned instance URL. Do not use legacy endpoints.
2. **Token TTL is 20 minutes; `expires_in` reports 1080 s (18 min) so you refresh two minutes early.** Cache and reuse — Salesforce names "a token per API call" as a direct cause of throttling.
3. **Scopes are the dominant failure mode.** A package scoped only for `email_read` will 403 on assets, journeys and contacts. `checkAuth` should report which scopes it proved, and `unsupportedResponse()` should distinguish "SFMC has no such endpoint" from "your package lacks the scope" — those are different problems with different fixes.
4. **A SOAP client is the unlock, and it is worth costing.** Six of the proposed ops (`getListMembership`, `listSuppressions`, `listBounces`, `listEngagementEvents`, `listSendingIdentities`, and the send-level half of `getPerformance`) are SOAP-only. Without one, SFMC's honest ceiling is journeys + assets + contacts + data extensions + transactional. With one, it is the most complete matrix of any platform in Orbit. The SOAP surface needed is narrow: `Retrieve` on ~10 objects against a single `Service.asmx` endpoint using the same OAuth token as REST (<https://developer.salesforce.com/docs/marketing/marketing-cloud/guide/authenticate-soap-api.html>).
5. **`ContinueRequest` paging.** SOAP `Retrieve` returns a maximum of 2,500 records per call; more requires the `ContinueRequest` property. Any SOAP-backed op must implement it or it will silently truncate (<https://developer.salesforce.com/docs/marketing/marketing-cloud/guide/continuerequest_2500records.html>).
6. **Journey history is a 30-day, 1 GB, non-resumable export.** Always call the estimate endpoint first; treat the op as `partial`, never `native`.
7. **Prefer `PATCH` over `PUT` on assets.** A full `PUT` requires resending the whole asset model; partial updates avoid blanking `slots`/`meta`.

# Klaviyo — public API capability survey

**Platform key:** `klaviyo`
**Base URL:** `https://a.klaviyo.com`
**Auth:** `Authorization: Klaviyo-API-Key <private-key>` (or OAuth for tech partners), plus a **mandatory** `revision` header
**API revision verified against:** `2026-07-15` (current stable)
**Verified on:** 2026-08-24
**Primary sources:**
- Machine-readable stable spec — <https://raw.githubusercontent.com/klaviyo/openapi/main/openapi/stable.json> (`info.version = 2026-07-15`, 238 paths / 345 operations). Every endpoint, scope and rate limit below is read from this spec.
- Human reference — `https://developers.klaviyo.com/en/reference/<operationId>` (URL convention confirmed live against `get_accounts` and `get_flow`, both showing revision 2026-07-15).
- API overview / auth — <https://developers.klaviyo.com/en/reference/api_overview>

**Conventions used below**
- **R / W** — read vs write. `POST` is not automatically a write: Klaviyo uses `POST` for query-shaped endpoints (`/api/metric-aggregates`, `/api/*-values-reports`, `/api/template-render`) that carry `*:read` scopes and have no side effects. Those are marked **R**.
- **Do not automate** — flagged on every endpoint that sends, deletes, merges, unsubscribes, suppresses, or flips a live journey.
- Every row carries the exact endpoint and a doc URL. Nothing here is inferred from a blog post or changelog.

## 1. The existing 8 operations — confirm / correct

| Op key | Orbit records today | Verdict | Correct endpoint (rev 2026-07-15) | Doc URL | Notes |
|---|---|---|---|---|---|
| `checkAuth` | `partial` — "no ping; probe = `GET /api/lists?page[size]=1`" | **CORRECT → `native`** | `GET /api/accounts` | <https://developers.klaviyo.com/en/reference/get_accounts> | Klaviyo documents this endpoint's purpose verbatim as "test if a Private API Key belongs to the correct account prior to performing subsequent actions with the API". It also returns the data Orbit wants at connect time: `contact_information.default_sender_name` / `default_sender_email`, `organization_name`, `street_address`, `timezone`, `preferred_currency`, `locale`, `public_api_key`, `test_account`. Scope `accounts:read`. Rate limit burst `1/s`, steady `15/m` — cache it. The `lists` probe still works but needs `lists:read` and tells you nothing about the account. |
| `listTemplates` | `native`, `GET /api/templates` | **CONFIRMED** | `GET /api/templates` | <https://developers.klaviyo.com/en/reference/get_templates> | Scope `templates:read`; burst `75/s`, steady `750/m`. Add `additional-fields[template]=definition` to get the block definition of `SYSTEM_DRAGGABLE` (Klaviyo-native drag-and-drop) templates — without it a DnD template returns rendered `html` only. `doc_url` in Orbit currently points at the generic `api_overview`; tighten it to the operation page. |
| `getTemplate` | `native`, `GET /api/templates/{id}` | **CONFIRMED** | `GET /api/templates/{id}` | <https://developers.klaviyo.com/en/reference/get_template> | Returns `name`, `editor_type` (`CODE` / `USER_DRAGGABLE` / `SYSTEM_DRAGGABLE`), `html`, `text`, `amp`, `created`, `updated`. Unlike Mailchimp, Klaviyo **does** return stored HTML on read. |
| `pushTemplate` | `native` — "`POST /api/templates`, `PATCH /api/templates/{id}`, **`POST /api/templates/{id}/render`**" | **CORRECT (stale endpoint)** | `POST /api/templates`, `PATCH /api/templates/{id}`; render is **`POST /api/template-render`** | create <https://developers.klaviyo.com/en/reference/create_template> · update <https://developers.klaviyo.com/en/reference/update_template> · render <https://developers.klaviyo.com/en/reference/render_template> | `POST /api/templates/{id}/render` **does not exist** in revision 2026-07-15 — the render endpoint is the top-level `POST /api/template-render` (body carries `template_id` + `context`; scope is `templates:read`, so it is a safe read). Two real constraints Orbit should record: (a) create/clone **fails once an account holds 1,000+ templates** — a hard API-created cap; (b) `html` is required for `CODE`/`USER_DRAGGABLE` and **not allowed** for `SYSTEM_DRAGGABLE`, which requires a structured `definition` instead. Scope `templates:write`. |
| `listCampaigns` | `native` — campaigns need a channel filter; flows separate | **CONFIRMED** | `GET /api/campaigns?filter=equals(messages.channel,'email')`, `GET /api/flows` | campaigns <https://developers.klaviyo.com/en/reference/get_campaigns> · flows <https://developers.klaviyo.com/en/reference/get_flows> | Channel filter is still **required** (`'email'` \| `'sms'` \| `'mobile_push'`). Campaigns: burst `10/s`, steady `150/m`, max `page[size]=100`. Flows are much tighter: burst `3/s`, steady `60/m`, max 50 per page — a full flow inventory on a large account needs pacing. |
| `listSegments` | `native`, `GET /api/segments`, `GET /api/lists` | **CONFIRMED** | `GET /api/segments`, `GET /api/lists` | segments <https://developers.klaviyo.com/en/reference/get_segments> · lists <https://developers.klaviyo.com/en/reference/get_lists> | Both native. Two caveats worth recording: `GET /api/lists` returns a maximum of **10 results per page**; and member counts are **not** in the default payload — `additional-fields[segment]=profile_count` (or `additional-fields[list]=profile_count`) is required and drops the rate limit to burst `1/s`, steady `15/m`. |
| `getPerformance` | `partial` — `POST /api/campaign-values-reports`, limits burst 1/s, steady 2/m, daily 225/d, `conversion_metric_id` required | **CONFIRMED (and under-claimed)** | `POST /api/campaign-values-reports` | <https://developers.klaviyo.com/en/reference/query_campaign_values> | Every recorded detail still holds: burst `1/s`, steady `2/m`, daily `225/d`, and `statistics` + `timeframe` + `conversion_metric_id` are all **required**. 30 statistics available incl. `delivered`, `delivery_rate`, `bounce_rate`, `spam_complaint_rate`, `unsubscribe_rate`, `click_to_open_rate`, `conversion_value`, `revenue_per_recipient`. What Orbit's row misses: the same shape exists for **flows, segments and forms** — see proposed `getJourneyPerformance`, `getAudiencePerformance`, `getFormPerformance` below. |
| `sendTest` | `unsupported` — nearest alt `POST /api/templates/{id}/render` | **CONFIRMED unsupported** (nearest-alternative string is stale) | — | <https://developers.klaviyo.com/en/reference/render_template> | Verified exhaustively: the stable spec contains **no** path matching `test`, `preview`, or `proof`. There is no way to proof a template or a draft campaign to an address via the public API. `POST /api/campaign-send-jobs` is a *real send to the campaign audience*, not a test. The nearest alternative is right in substance but wrong in path — it must read `POST /api/template-render` (+ Orbit's local `orbit_render_email_preview` / `orbit_qa_email`). |

**Score: 6 confirmed, 2 corrected** (`checkAuth` endpoint + support level; `pushTemplate` render path), plus one stale endpoint string inside `sendTest.nearest_alternative`.

| **Sending-domain / DKIM / SPF / BIMI status** | **unsupported** | The spec contains **zero** occurrences of `sending domain`, `dkim`, `spf`, `deliverability`, or `dedicated` — there is no sending-identity or domain-authentication resource at all. | `GET /api/accounts` gives the default sender email (hence the domain); authentication itself must be verified out-of-band via DNS — Orbit's `orbit_check_email_auth` / `orbit_check_bimi`. Doc: <https://developers.klaviyo.com/en/reference/get_accounts> |

| **Custom metrics in event filtering / aggregation** | **unsupported** | Klaviyo states it explicitly on both endpoints: custom metrics "are not supported in the `metric_id` filter" (`get_events`) and are "not supported at this time" (`query_metric_aggregates`). | Aggregate the underlying source metric instead; read custom-metric definitions via `GET /api/custom-metrics` for context only. Doc: <https://developers.klaviyo.com/en/reference/query_metric_aggregates> |

Doc: <https://developers.klaviyo.com/en/reference/get_campaigns> |

## 4. Operational notes worth recording in the matrix

- **Revision header is mandatory on every call.** Format `YYYY-MM-DD[.suffix]`; verified stable is `2026-07-15`. An adapter must pin a revision explicitly — omitting it fails, and drifting it silently changes response shapes.
- **Rate limits are per-endpoint and vary by three orders of magnitude.** Events `350/s` burst; templates/profiles `75/s`; flows and forms `3/s`; webhooks, web-feeds, metric-properties and any `profile_count` / `include=list` request `1/s` + `15/m`. All six `*-values-reports` / `*-series-reports` endpoints share the punitive `1/s` burst, `2/m` steady, **`225/d`** daily budget — reporting must be cached and batched, and a naive per-campaign loop will exhaust the day.
- **Scopes are granular.** `accounts:read`, `templates:read/write`, `campaigns:read/write`, `flows:read/write`, `lists:read/write`, `segments:read/write`, `profiles:read/write`, `metrics:read`, `events:read`, `webhooks:read`, `images:read/write`, `catalogs:read`, `coupons:read`, `forms:read`, `tracking-settings:read`, `conversations:read`, `custom-objects:read`, `reviews:read`, `web-feeds:read`. A key scoped only to templates will fail `getAccount` — the auth-check error must say which scope is missing rather than "auth failed".
- **Pagination is cursor-based** (`page[cursor]`, `page[size]`), with per-resource caps: lists 10, flows / flow-actions 50, tags 50, campaigns 100, catalog items 100, metrics 200, events 200.
- **JSON:API envelope throughout** — `data.type` / `data.id` / `data.attributes` / `data.relationships`, with `include=` for compound documents and `fields[type]=` sparse fieldsets. Sparse fieldsets support deep dotted paths (e.g. `fields[campaign-message]=definition.content.subject`), which is the cheapest way to keep responses small under Orbit's context budget.
